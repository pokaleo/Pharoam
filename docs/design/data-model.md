# Data model

| | |
|---|---|
| **Version** | 0.1 (in discussion) |
| **Source** | [PRD](../PRD.md) · [Architecture](../ARCHITECTURE.md) AD6, AD7, AD16 |
| **Status** | The logical model. Concrete Zod schemas are derived from it during implementation. |

## 0. Guiding rule: the data belongs to the person, not to Pharoam

**Everything stored in the user's storage must be human-readable, self-explanatory and useful without Pharoam** ("anywhere, anytime, anyone"). Pharoam is a tool the person uses on their data; they are free to take the data anywhere, for any purpose.
- No opaque, system-specific blobs (serialised engine state, binary caches, internal IDs without meaning).
- Field names are plain English, and values are readable (dates, levels, words rather than codes).
- Machine-specific working state lives **only in the disposable local cache** (AD9). Pharoam must be able to rebuild it from the readable records.

## 1. Record types

| Group | Type | Purpose |
|---|---|---|
| **Profile** (user's storage) | `pharoam` | **The central record about the person** (`pharoam.md`): one per profile. Holds the format version, preferences, the person's headline and current situation in their own words, and an overview that Pharoam regenerates. **It never holds a name, photo or other directly identifying data.** All other records enrich it. |
| | `evidence` | Something studied or done, linked to skills and carrying no level. Kinds: degree, module, certificate, job, project, repository, publication, reflection, **assessment** (a diagnostic's full record), other |
| | `skill-record` | One per skill the person has: the append-only history of **observations** (one provenance-labelled statement about the skill at one level) and **reviews** (retracting an observation), plus the generated shown level, see §6 |
| | `aspiration` | An interest, goal or constraint |
| | `plan` | A learning plan toward a chosen pathway |
| | `session` | A **readable progress record** of an unfinished workflow (for example a diagnostic, or AI judgements awaiting review): what has happened so far and what comes next. Pharoam rebuilds its working state from it, so it can be resumed on any device. It contains no engine checkpoint (§0). |
| | `gap` | A stored gap analysis for one pathway being explored, readable outside Pharoam (§10) |
| **Content** (packs) | `skill` | Skill-inventory entry |
| | `pathway` | Career pathway |
| | `assessment-item` | A question or task |
| | `resource` | Learning material (later) |
| | `pack` | Pack manifest |
| **Generated** (stored, regenerated by Pharoam) | proficiency summaries (the shown level) | Inside each `skill-record` (§6) |
| | `gap` | See above. Regenerated when the profile or pathway changes. |

## 2. IDs and references

- **Profile records:** UUIDv7 (RFC 9562), written in lowercase. Sorts by creation time and can be generated in the browser. IDs made in the same millisecond still sort in the order they were made (RFC 9562 §6.2, method 2).
- **Content records:** readable slugs (for example `python`, `ml-engineer`, `py-closures-01`): lowercase letters and digits joined by single hyphens, at most 64 characters, so a slug is also a safe file name.
- **References always use IDs, never file names**, so renaming or moving a file breaks nothing.

## 3. Common envelope

Every record is a **Markdown (`.md`) file**. Its structured fields sit in the block between the `---` lines at the top of the file, written in YAML syntax (Obsidian shows it as Properties). The text below the block is normal Markdown. Every record's top block starts with:

```yaml
schema: evidence/1          # record type + format version
id: 0192f3a1-7c2e-7b44-9a1d-3e5f6a7b8c9d
created: 2026-10-24T14:02:11Z
updated: 2026-10-24T14:02:11Z   # editable records only
ai: null                     # or an AI provenance block (§5)
# …type-specific fields…
```

## 4. History and editing

The user controls their storage, so **any file can be edited or deleted by hand**. The rules below describe what *Pharoam* does.

| Record | Pharoam edits it? | Notes |
|---|---|---|
| Observation and review entries in a `skill-record` | **Never** (only appends new entries) | The audit trail. Corrections are new entries (`supersedes`, or a `retract` review). |
| `evidence` of kind `assessment` | **Never** | The proof of a diagnostic: the items, answers, marking and result |
| Other `evidence`, `aspiration`, `plan`, `pharoam` | Yes | `updated` changes on each edit. In `pharoam.md`, Pharoam only rewrites the marked overview section and its own fields, never the person's own text. |
| `session` | Yes, until the workflow ends | Then deleted or archived |

- **Deletion is real.** References to a deleted record show as "removed" and never cause an error.
- **Manual edits to records Pharoam never edits.** Pharoam stores an `integrity` fingerprint (below) when it creates such a record or entry. On a mismatch, the record is labelled **"edited outside Pharoam"**; it is still used, but the change is visible. This catches casual edits, not deliberate tampering. Signing comes later (P15).
- **Invalid records** (broken syntax, a missing or wrong field) are **never deleted or overwritten**. They appear in a **"Needs attention"** list with a plain explanation. The user fixes them by hand, or accepts a fix Pharoam proposes. Until then they are left out of calculations. Fields Pharoam doesn't recognise are always kept unchanged.

### Integrity fingerprint

The value is `sha256-c1:` followed by 64 lowercase hex digits. `c1` names the rule below. A changed rule gets a new name; old values are still checked with the rule they name.

1. **What is fingerprinted:** for a `skill-record` entry, that entry; for an assessment record, an object `{ "top": <top block>, "body": <body> }`.
2. **Left out:** the `integrity` and `signature` fields of the entry, or of the assessment record's top block. A future signature signs the same form.
3. **Parsed values, not text:** YAML 1.2 core schema, so dates and times stay the strings written, and `yes` stays a string. Aliases are resolved. A duplicate key makes the record invalid (Needs attention), never fingerprinted.
4. **Body text:** line endings become LF and trailing newlines at the end are removed. Nothing else changes; text is not Unicode-normalised.
5. **Canonical form:** the result is serialised with the JSON Canonicalization Scheme (RFC 8785): keys sorted, no whitespace, one way to write each number. The fingerprint is the SHA-256 of its UTF-8 bytes.

So **layout doesn't count as an edit**, but values do: quoting, indentation, comments, key order and line endings can change without a mismatch; changing any value, or adding or removing any field (including ones Pharoam doesn't know), is reported.

An entry or record **without a valid fingerprint** was added outside Pharoam and is labelled the same way. A fingerprint naming a rule this Pharoam doesn't know, for example one written by a newer version, is reported as not checked rather than as edited.

## 5. AI provenance

Any record that AI created or changed carries an `ai` block. Its Markdown body also starts with a visible disclaimer, so the AI origin is clear outside Pharoam too (PRD D6).

```markdown
---
schema: evidence/1
id: 0192f3a1-…
ai:
  task: normalise-evidence@1     # registered task + version (AD4)
  model: anthropic/claude-sonnet-5-5
  at: 2026-10-24T14:02:11Z
  confirmed_by_user: 2026-10-24T14:03:40Z
kind: job
title: Backend Engineer
---
> ⚠️ AI-generated from your pasted text and confirmed by you. AI can make mistakes.

Built and ran the payments API…
```

`confirmed_by_user` records when the person confirmed the output; an `ai-judged` observation is written only at that moment (PRD D2). A diagnostic result needs no confirmation (PRD E7), so its `ai` block has none.

## 6. Skill records (one file per skill)

Each skill the person has is **one `.md` file** (`skill-record`). Its top block holds the skill (`skill`, its inventory slug) and an **append-only list** of its observations and reviews (`entries`), and its body shows a readable summary of the skill's history. Pharoam appends entries and never changes existing ones. Each entry carries its own `integrity` fingerprint (§4).

### Provenance

| `provenance` | Comes from | Tested? | Counts |
|---|---|---|---|
| `self-reported` | The person's own rating | No | When recorded |
| `ai-judged` | An AI task scanning the person's evidence (PRD D1) | No | When the person accepts it; it is written only then (PRD D2) |
| `demonstrated` | A question-bank diagnostic, marked by a fixed, published rule (PRD E2) | Yes | When the diagnostic ends |
| `ai-correlated` | An AI-led diagnostic (PRD E3) | Yes | When the diagnostic ends |

### Entries

Observation entry fields:
- `id`, `level` (0–4), `provenance`, `observed_at`
- `evidence`: references to evidence records the observation cites (optional for every provenance)
- `assessment`: the diagnostic's evidence record (required for `demonstrated` and `ai-correlated`)
- `explanation` (required for `ai-judged` and `ai-correlated`) and `limits` (required for `ai-judged`)
- `ai`: the AI provenance block (§5; required for `ai-judged` and `ai-correlated`)
- `supersedes`, `integrity`
- `signature: null` (reserved)

Review entries hold `id`, `target` (an observation ID), `decision: retract`, `reviewed_at` and an optional `note`. AI judgements awaiting a decision are not entries; they wait in a review `session` (§10).

### Shown level

Each skill shows **one level**, chosen from the observations that count (retracted and superseded ones never do) in this order:

1. the latest `demonstrated` or `ai-correlated` observation;
2. otherwise, the latest `ai-judged` observation;
3. otherwise, the latest `self-reported` observation.

"Latest" means the most recent `observed_at`, so a retaken diagnostic replaces the earlier result. When the shown level is tested, the latest claim (`self-reported` or `ai-judged`) newer than it that differs from it is recorded as `newer-claim` and shown as a note on the level, never as the level. The order is a fixed rule, not a calculation: no level is ever blended from several entries (Charter R4).

### Proficiency summary

Each skill file has a **`proficiency`** block in its top block. Pharoam regenerates it whenever the history changes, so it's readable in Obsidian or Notion without Pharoam. It holds the shown level, any newer claim, the latest level from each source, and an optional `target` level set by the person or a plan:

```yaml
proficiency:                     # generated by Pharoam; don't edit
  shown:
    level: 2
    provenance: ai-correlated
    since: 2026-10-20
    observation: 0192f3c4-…
  newer-claim:                   # only when a newer claim differs from a tested shown level
    level: 4
    provenance: self-reported
    since: 2026-10-24
  by-source:                     # latest counting level from each source
    self-reported: { level: 4, since: 2026-10-24 }
    ai-judged:     { level: 3, since: 2026-10-05 }
    demonstrated:  { level: 2, since: 2026-10-12 }
    ai-correlated: { level: 2, since: 2026-10-20 }
target: 4
```

The body shows the skill's history newest first, with the entry behind the shown level marked (PRD C6).

What each level means for a specific skill comes from that skill's **level descriptors in the skill inventory**, so levels mean the same thing across profiles.

## 7. Evidence

Each evidence item is **one `.md` file**. Evidence records what the person did; it **carries no level** (Charter R4).
- **Common fields:** `kind`, `title`, `organisation`, `start`/`end` or `date` (to the year, month or day: `2024`, `2024-09` or `2024-09-30`), `links` (`http` or `https` only), `skills`, `attachments`, and `source` (`manual`, `paste` or `import`; where the original input is kept goes in `original_input`).
- **`skills`** lists the skills the item involved. They are entered by hand or proposed by AI and confirmed by the person (PRD B6). Confirmed AI-proposed links are also listed under `ai-skill-links` with the task, model, time and `confirmed_by_user`, so the record shows which links came from AI without labelling the whole record AI-made. AI tasks use these links to find a skill's evidence locally, without sending the whole profile (PRD D4).
- **Extra fields per kind:** for example a module's course code, credits and grade; a certificate's issuer, credential ID and expiry; a repository's URL and the person's role.
- **`assessment` evidence** is the full record of one diagnostic, in the top block for exact proof:
  - `diagnostic`: `question-bank` or `ai-led`, the skill, and the starting level;
  - each step of the adaptive path: the item (its bank ID, or the full text of an AI-written item), the answer, the marking and its reasons;
  - the result level and, for a question bank, the marking rule that produced it;
  - for an AI-led diagnostic: the evidence and earlier results it considered, the explanation (PRD E5) and the `ai` block.

  The body shows a readable summary.

## 8. Folder layout (file connectors)

```
Pharoam/                              ← the folder the user chooses
├── pharoam.md                        ← the central record about the person
├── skills/
│   ├── python.md                     ← history + proficiency for one skill
│   └── postgres.md
├── evidence/
│   ├── backend-engineer-example-co--6a7b8c9d.md
│   ├── diagnostic-python-2026-10--4e1b9a07.md
│   └── _attachments/0192f3a1/original-input.txt
├── aspirations/
├── plans/
├── gaps/                             ← stored gap analyses, one per pathway explored
└── sessions/                         ← unfinished workflows (e.g. a paused diagnostic)
```

- Skill files are named by skill slug, and gaps by pathway. Other files are named by a readable title plus a short ID: the last 8 hex digits of the record's UUIDv7, its random part (the first digits are a timestamp that records made within a minute share). Pharoam relies only on the IDs inside the files.
- Records are found anywhere in the folder. Hidden folders (such as `.obsidian` or `.git`) and `_attachments` are skipped.
- The layout is open to new folders for future features, for example generated CVs and a saved jobs bank (PRD H).

## 9. Skill references

Profile records reference skills by **Pharoam inventory slug only** (for example `skills: [python, postgres]`). Cross-references to ESCO, Wikidata and GitHub topics live in the inventory, so profiles never need rewriting when a mapping changes.

**Custom skills.** A skill the inventory lacks can be added by the person. Its slug starts with `custom-` (for example `custom-kdb-q`), and its skill record holds `name` and an optional `description` in the top block. Custom skills are marked as the person's own and never match pathway requirements, which name inventory skills only ([MVP](../MVP.md) S8).

## 10. Other profile records

### `pharoam` (the central record, `pharoam.md`)
- `headline`: the person's own one-line summary.
- `situation`: `stage` (`studying`, `working`, `between-roles` or `changing-career`), plus `field`.
- `region`: optional, **country only**, as an ISO 3166-1 two-letter code such as `GB` (pathway costs, salaries and qualifications vary by country).
- `focus`: pathways or skills currently being explored.
- `preferences`: mode, language, chosen model provider (never the key).
- **Never:** name, photo, contact details or exact location.
- Body: the person's "About me", plus a marked overview section that Pharoam regenerates.
  - The section sits between `<!-- pharoam:overview -->` and `<!-- /pharoam:overview -->`, each starting a line. Most Markdown viewers, Obsidian included, don't show these comments; Pharoam's own renderer removes them (raw HTML stays off).
  - Pharoam writes only between the markers, so the person's text before or after them is never changed. Without markers, it adds the section after the person's text. With broken markers (one missing, out of order or repeated), it changes nothing and says why.
  - The overview gives the number of evidence records and skill records and the date of the last change to either, in the person's language. It is regenerated whenever evidence or skills change.

### `aspiration`
- `kind`: interest, goal or constraint (for example "can study at most 5 hours a week").
- `statement` in the person's own words.
- Optional linked pathways or skills.
- `horizon`: now, 1 year or long term.
- `status`: active or archived.

### `plan`
- Target pathway, pinned to a version (`pack@version:pathway`).
- Target level per skill, pre-filled from the pathway and editable.
- `steps`: skill, activity, linked resources, status.
- `status`: active, paused, done or abandoned.
- **Progress is calculated** from new observations, never ticked off by hand alone (PRD G3).

### `gap` (generated)
- One per pathway being explored, with the pathway pinned to a version.
- `requirements`, one per pathway requirement: `skill`, the `required` level, the skill's `shown` level and its provenance (or `null`), the `group` (*supported*, *claimed*, *below* or *unknown*; PRD F3), and the `evidence` a claimed level cites.
- **Regenerated automatically** when the profile or the pathway changes, always shown to the user ("Updated just now"), with a manual refresh button. It needs no AI.
- The body shows a readable summary, so the analysis is useful in Obsidian or Notion.

### `session`
- Workflow name and version, `status` (in progress, completed or abandoned), started and updated times.
- **AI review session:** the AI judgements and skill links from an evidence scan that await the person's decision (PRD D2), each with its explanation, limits and `ai` block, and the decision once made. Accepted items are written to the skill and evidence records; skipped items stay here, pending.
- **A readable log of what has happened so far**: for a diagnostic, the items asked, the answers given and the marking so far, plus what the next step is.
- Pharoam rebuilds its working state (for example a LangGraph checkpoint) from this log. Any engine checkpoint is kept only in the local cache.
- When the session completes, its results are written as evidence and observations. The session is then archived as a readable record, or deleted if the person chooses.

## 11. Content records

### `skill` (inventory entry)
- `slug`, `name`, `aliases`, `description`, `domain`.
- `relations`: implies or related skills.
- **`levels`**: descriptors for levels 0–4 specific to this skill.
- `refs`: ESCO URI, Wikidata ID, GitHub topic.
- `origin`: source (for example the MIND fork) and licence attribution.
- `status`: active, or deprecated with `replaced_by`, so old profiles keep working.

### `pathway`
- `slug`, `title`, `summary`.
- `requirements`: skill, level, importance (core or helpful).
- `prerequisites`, `transferable` skills, `uncertainties`.
- `investment`: time and cost ranges, **each with sources**.
- Linked ESCO occupations, `sources`, `review` (who reviewed it and when), and the AI block if AI drafted it.

### `assessment-item`
- `slug`, `skills`, targeted `level`, `format` (mcq, practical or open), `prompt`.
- Multiple choice: `options` and `answer`. Multiple-choice items make up the **question bank** for question-bank diagnostics; AI-led diagnostics can use them too.
- Practical and open: a **`rubric`** the AI marks against.
- `language`, `origin` and licence, and the AI block if drafted.

### `pack` (manifest)
- `name`, `version`, `min_app_version`, `licences` (one per data source), contents, available translations.
